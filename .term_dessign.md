# The problem
A FE problem is defined by a bilinear form `a(u,v)` and a linear form `l(v)`, where u and v are trial and test functions respectively. a and L are tipycally defined by integrals. The matrix of the discrete problem is formed by replacing u and v by basis functions. My current approach forces the user to define u and v as ShapeFunctions. In this way, the bilinear form a is build inside-out: differential operators applied to ShapeFuncions define new ShapeFunctions (storing information about the operator), and operations between ShapeFunctions or between ShapeFunctions and Number/Array/Function produce an Operation, with the structure of a tree. Then, an Integrand wraps the Operation. Multiplication of an Integrand and a Measure defines a Term. And a sum of Terms produces a Form.
This is convenient, I think, because the integration can be then performed in a Term by Term manner. Terms with variable coefficients (Functions) or constant coefficients (numbers/arrays) follow different paths. Similarly: different combinations of differential operators produce local tensors and "collapsers" of different shapes, so the actual mechanics of the assembly is slightly different for different Terms.
However, one problem remains: the actual evaluation of an Operation. This requieres ShapeFunctions to be replaced by actual PolyScalarFields and the tree to be evaluating by appling differential operators and operations to the PolyScalarFields, producing Tensors with eltype <: PolyScalarField. This Tensors can then be integrated over each mesh element. The problem is that the replacement of ShapeFunctions by basis elements is not trivial. For example, a user can write `∫(∇(u)⋅∇(v))*dΩ`, producing the Operation tree `(*,∇(u),∇(v))` or `∫(∇(v)⋅∇(u))*dΩ`, producing the Operation tree `(*,∇(v),∇(u))`. The two bilinear forms are exactly the same, but the Operations are not. In other words: when unrolling `u` and `v` into their corresponding basis elements I cannot replace them in the operation assuming a predetermined order.

# Possible solutions
## Option 1:
Make the user define bilinear (and linear) forms as functions:
```julia
a(u,v) = ∫(∇(u)⋅∇(v))* dΩ
```
Then simply evaluate this function on basis elements. For this I would need to properly define productos of Tensors with eltype <: PolyScalarField as otimes, to produce local tensors. This looks clean... but it seems to break the whole structure of Forms. Indeed: currently I can inspect a Form and separate it in Terms, with different dispatch for each of them. Then, I can break a Term into Operation and Measure, inspect the Measure, iterate along its elements and THEN evaluate the Operation for integration on each mesh element. On the contrary, evaluation of function `a` would make the Measure accessible only AFTER producing a concrete Tensor (which does not seem possible, since the concrete basis elements must be deduced from the mesh).
## Option 2:
Distinguish ShapeFunctions either by:
i) introducing a trait `Trial`/`Test` so `u` and `v` are actually of different type, or
ii) replacing ShapeFunction entirely by two new structs: `TrialSpace` and `TestSpace` with similar mechanics.
The problem of actually replacing ShapeFunction/Spaces by basis elements remains, but at least this would allow to distinguish which ShapeFunction/Space should be replaced by which basis.

The actual replacement can be perform by traversing the tree, inspecting its elements and replacing them. An alternative would be to try to somehow mimic the advantages of Option 1: inspect the Operation and produce a Function of arguments `(u,v)` that can then be just evaluated. This would carry the advantage of traversing the Operation only once, and then evaluating many times (on each pair of element basis).  A possible problem would be to define a closure, which I think would produce some inference problems for the compiler.
