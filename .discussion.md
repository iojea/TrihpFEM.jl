A) I == Int32 impose a hard limit on mesh size, since DOFs are numerated with I, and the number of DOFs behaves as p^2, so high degrees reduces considerably the possible number of triangles. Int32 is the standard of Triangulate.jl. This is not a great problem, because the initial mesh will be relatively small, but the rest of code inherits Int32 from Triangulate. So we also discussed the possibility of adding support for other backends.

================================================================
1. "Convert Int32 → UInt32/UInt64 right after construction" — agree, with a choice of default
================================================================

Widening the index type post-construction is the correct move and avoids fighting Triangulate. Two notes:

- After construction you only need to widen I (the point/edge/triangle index) and possibly P (degree). The DOF global counters (dofs.n::RefValue{I}) and the by_edge/by_tri index arrays all key off I, so widening I takes care of the dof-overflow risk. Widening P from UInt8 to UInt16 (degree ≤ 65535, far beyond the p~15 practical ceiling) is cheap insurance and removes the silent degree wrap.
- I'd default the converted type to Int64, not UInt32. Reasons: (a) Vector indexing in Julia is 1-based signed Int; using UInt32 for point indices is fine for storage but Julia array indices are Int (signed), so you'd be doing points[k] with a UInt32 k — that works but is slightly unnatural and can surprise generic code; (b) Int64 gives the ~9×10¹⁸ headroom with zero risk, and the memory cost vs Int32 is 4 bytes/vertex-reference — modest at research scale. If you truly want to halve storage on a memory-bound huge mesh, UInt32 works, but Int64 is the safer default. Your UInt64 is also fine; Int64 is just more idiomatic for Julia indices. Offer it as a choice, default Int64.
- You need the conversion routines (a convert(::Type{HPMesh{F,NewI,NewP}}, mesh) or Base.convert method, plus widening the DOF, TriangleList, EdgeList, and the SVector/MArray index arrays). Note DOF.I and the SArray{S,I,1} in by_edge must widen consistently or you'll have a mixed-I mesh. This is the one place the conversion has teeth — it must be total (every stored I becomes NewI). Worth a single well-tested helper.

================================================================
2. "Future: other meshing backends via extensions" — good direction, but design now, don't build now
================================================================

Agree it's the right long-term shape. The current HPMesh{F,I,P}(tri::TriangulateIO) constructor (mesh.jl:85) already isolates Triangulate behind one conversion point. That's the seam to exploit: define a small interface (e.g. "a mesh backend yields points + triangle list + edge list + markers") and make hpmesh build the HPMesh from that abstract description rather than from TriangulateIO specifically. Then a DelaunayTriangulation backend (or Gmsh, or HMTriangulation) is just another provider of that description.

Concrete suggestion so you don't paint yourself into a corner:
- Keep the TriangulateIO constructor as one implementation, but route hpmesh through a thin mesh_from_description(points, triangles, edges, markers; I, P) builder that both Triangulate and a future backend call. That makes the backend swappable without touching HPMesh internals.
- If you want true extension isolation (don't want Triangulate as a hard dependency for users who only use backend X), the natural move is what you said: put each backend in its own module/extension that imports TrihpFEM and adds a hpmesh method. Dictionaries.jl-style or an @require/extensions pattern. That's a clean future, but I'd only do it when the second backend actually appears — premature modularization is its own cost. The cheap thing to do now is just not let TriangulateIO leak deeper than the one constructor.

One risk to name: maybeconvert(I, edgelist) (mesh.jl:407) and eltype(tri.edgelist) assume the Triangulate integer type. If a backend emits a different integer type, the user-chosen I should win and the import should convert to it. So make the chosen I the authority at import time, not the backend's type.

B) PolyFields.jl produce the following important observations:
1. YOU'RE RIGHT — SArrays ARE THE WRONG CALL HERE
================================================================

At p1=p2≈15 the reference-cell local tensor is dim×dim×... where dim ≈ compute_dimension ≈ O(p²) ≈ 225, so a tensor of basis functions is ~225 components, and the contraction tensors are 2×2×dim×dim or 4×dim×dim — well into the hundreds-to-thousands of elements. My "just use SArray" was naive about the p=15 regime. Your middle-ground rationale is correct.

The only refinement I'd still make: FixedSizeArrayDefault is runtime-typed (it erases the element type/size from the static type), which is what blocks inference. C) Discussing how to carry around type information for dispatch in assembly, we agree to use DiffOperators instead of number tuples (Order). Also:

================================================================
FIRST: YOU'RE RIGHT THAT T CAN BE BIOLY OR POLYSUM
================================================================

The element type of a "field tensor" depends on which operator was applied to the basis functions:
- Identity(φ) = φ → BiPoly
- Gradient(φ) = [∂xφ, ∂yφ] → vector of BiPolys
- Divergence(v) = ∂x(v₁)+∂y(v₂) → PolySum
- Laplacian(φ) = Δφ → PolySum

So an outer product like ∇φ ⊗ ∇ψ has BiPoly entries; Δφ ⊗ Δψ has PolySum entries; and a mixed form like ∫(Δu · v) gives Δφ ⊗ ψ = PolySum entries. Both BiPoly and PolySum genuinely appear as elements. Your observation is correct.

================================================================
KEY FACT: WITHIN ONE POLYTENSOR, T IS ACTUALLY UNIFORM
================================================================

This is what resolves the design. In ref_tensors, each factor comes from one fixed operator applied to a whole basis:
- operator o₁ is fixed for the trial shape function → o₁(φ) has the SAME type for every φ in the basis,
- operator o₂ is fixed for the test shape function → o₂(ψ) has the SAME type for every ψ.

So o₁(φ) ⊗ o₂(ψ) always produces entries of type typeof(o₁(φ)) * typeof(o₂(ψ)) — the same type for every (φ,ψ) pair in that one tensor. Therefore a single PolyTensor has a single, concrete element type T. It's just that different PolyTensors (different Terms) may have T = BiPoly vs T = PolySum.

So you never need a PolyTensor whose entries are mixed BiPoly and PolySum within the same instance. That's the invariant that makes concrete-per-instance typing viable.

================================================================
SO: ABSTRACT-T vs CONCRETE-T WITH PROMOTION
================================================================

Your option (a) — make T an abstract type (e.g. PolyTensor{N, PolyScalarField}):
- Don't. Parameterizing the instance on an abstract element type is exactly the FixedSizeArrayDefault/Form.terms mistake we've been fixing: it erases the element type, defeats inference in the hot inner loop, and you're back to boxes. The abstract is fine in method signatures (outer(a::PolyTensor{N,<:PolyScalarField}, ...)), just not as the stored T of a concrete instance.

Your option (b) — keep T concrete, with a concrete type others promote to:
- This is the right call, and it's the standard Julia idiom. Concretely:
  - PolyTensor{N, T} where T is always instantiated as a concrete leaf (BiPoly or PolySum), never the abstract.
  - Define a promotion so the two can combine: Base.promote_rule(::Type{BiPoly}, ::Type{PolySum}) = PolySum. This is the "concrete type to which the others promote" you described. It's correct because multiplying a BiPoly by a PolySum distributes to a PolySum ((p::PolyScalarField, q::PolySum) = PolySum(pq.left, p*q.right), fields.jl:286), so PolySum is genuinely the wider representation.
  - Write the generic methods (outer, contract, ref_integrate, the *) on the abstract PolyScalarField (or PolyField), so they apply to whichever concrete T an instance carries.
  - When outer/contract meet two PolyTensors of different T, compute promote_type(Ta, Tb) and build the result as PolyTensor{ra+rb, promote_type(Ta,Tb)}.

This gives you: each instance has a concrete, inferrable T (no abstraction penalty), and combining BiPoly- and PolySum-tensors just promotes to PolySum via the rule. No abstract-type parameterization, no inference loss, full generality across the two field kinds.

================================================================
ONE SCOPE BOUNDARY TO KEEP
================================================================

Keep T <: PolyScalarField only — i.e. BiPoly and PolySum. GeneralField (Function ∘ poly, variable coefficients) stays outside PolyTensor, handled at the Term/CoeffType level via quadrature, exactly as we concluded in the Forms discussion. So a PolyTensor's elements are always exact symbolic fields (BiPoly/PolySum), never unevaluated functions. That preserves the exact-integration property (ref_integrate on BiPoly/PolySum is exact) and keeps the element-type set to exactly two concrete types with a clean promotion — not an open-ended Any.

================================================================
VERDICT
================================================================

- You're right T can be BiPoly or PolySum.
- The reason it's manageable: within one PolyTensor, T is uniform (operator fixed per shape function → all entries share a type). So you never store a mixed instance.
- Therefore: don't parameterize on the abstract type (kills inference). Do keep T concrete per instance, with promote_rule(BiPoly, PolySum) = PolySum, and put the generic arithmetic/integration methods on PolyScalarField. This is precisely your option (b), refined to "concrete-per-instance + promotion" rather than "abstract T."
- This preserves inference AND handles both field kinds, and it's the minimal, idiomatic design.

D) We discussed ownership of meshes and how to avoid making a mess of it. The solution is to add a gen (generation) index to the mesh AND a lock (bool). gen is bumped on each modification. This helps the program sync with DOF and with Problem, in order to error or autoupdate when trying to solve a async problem. lock is meant to prohibit user modification of the mesh after the mesh is handled to a problem. The last details are as follows:

Yes, the split is correct — and your instinct to separate "what does the mutation" from "who is allowed to ask for it" is exactly the right axis. Let me refine the framing slightly so the solver never reaches into internals, which makes the ownership contract cleaner than "solver calls _refine! on the raw variable."

================================================================
THE CLEAN VERSION: DISPATCH ON OWNER, NOT ON "INTERNAL VS PUBLIC"
================================================================

Keep the structural mutation in ONE private routine, and expose TWO public refine! methods — one per owner type. The lock check lives only on the mesh-facing method; the problem-facing method is inherently authorized because the problem owns the mesh:

    # private, unexported — the single source of truth for topology mutation
    function _refine!(mesh::HPMesh)
        # ...current refine! body (red/blue/green + filter!)...
        mesh.gen += 1          # bump version on EVERY mutation
        return mesh
    end

    # public — user entry point, pre-problem
    function refine!(mesh::HPMesh)
        mesh.locked && error("mesh is locked: refine the owning FEProblem, not the mesh.")
        return _refine!(mesh)
    end

    # public — adaptive solver entry point, post-problem
    function refine!(prob::AbstractProblem)
        m = domainmesh(prob)
        _refine!(m)                 # no lock check: prob owns m
        prob.gen = m.gen           # keep problem in sync with its mesh
        update!(prob)              # reassemble K, rhs (feproblem.jl:60)
        return prob
    end

Why this is better than "solver calls _refine!(prob.mesh) directly":
- The solver calls the public refine!(prob) — it never touches prob.mesh internals. Cleaner, and the "who may mutate" decision is made by method dispatch, not by the caller remembering to use the underscore version.
- The lock guard is colocated with the only entry point a misusing user could reach (refine!(mesh)). The problem's refine! simply doesn't check lock, because it's an authorized entry operating on its own mesh.
- It generalizes: a future BoundaryMesh or Estimator that owns a mesh gets its own refine! method reusing _refine! — no new lock logic.

================================================================
TWO-LAYER SAFETY STAYS (lock + gen)
================================================================

This split handles public misuse (the locked guard). But the gen check is the second net for internal bypass:
- If a user pokes mesh.trilist[...] = ... directly (bypassing refine!, so locked never fires), the public guard can't catch it.
- That's why solve/assembly_matrix (feproblem.jl:36) still assert mesh.gen == prob.gen and error on mismatch. The gen check catches the internal bypass the lock can't.
- So: locked = "stop public edits after handoff"; gen = "catch any edit, public or smuggled, that desynced a derived object." Both layers needed.

And note _refine! itself does NOT check locked — it's lock-agnostic by design, so refine!(prob) can drive it on a locked mesh. That's the whole point: the lock is a property of the public mesh entry, not of the mutation primitive.

================================================================
ONE MORE: THE COPY VERSION
================================================================

refine(mesh) (copy+mutate, refine.jl:238) should also respect the contract. If mesh.locked, it's spawning a divergent mesh from a problem-owned one — the same "two meshes, no tie" problem. So:
    refine(mesh::HPMesh) = (mesh.locked && error(...); out = copy(mesh); _refine!(out); out)
Keep it for one-off pre-problem use, but it shares the same guard. In the adaptive loop you use refine!(prob), never refine.

================================================================
VERDICT
================================================================

- Your proposal is correct: separate the structural mutation (_refine!, no checks) from the guarded public entry (refine! checks lock).
- Make it cleaner by dispatching the authorized path on the owner: refine!(prob) (not "solver calls _refine! on the raw variable"). The solver only ever calls public methods.
- _refine! is the single unexported routine doing mutation + gen bump; both public refine! methods delegate to it.
- Keep the gen mismatch check at solve/assembly as the second safety net for internal bypass.
- This gives: in-place (performant) refinement, a loud error on public misuse, and a loud error on smuggled misuse — without copying per iteration. Exactly the deal.II/p4est discipline, Julia-adapted.
